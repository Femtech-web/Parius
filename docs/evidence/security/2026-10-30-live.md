## Method and scope

Three new fictional accounts represented freelancer A, client B and outsider C. A and B joined one new project; C owned another. Valid controls used ordinary signed-in Supabase clients before requests crossed a boundary. Administrator access only created and disabled the disposable identities; it was not used for attack requests or owner-side comparisons. The script did not query or modify existing user projects.

The fixture had an approved fictional USD agreement and a manual invoice labelled **do not pay**. It had no funds, payment requests, uploads, confirmed memories or AI jobs. This avoided transfers and paid-provider work. Invalid role and outsider writes were followed by normal owner reads to check that the attempted change had not occurred.

## Cleanup and reproduction

The fixture connection was revoked. All three test accounts were signed out and their administrator disablement calls succeeded. Existing access JWTs may survive sign-out until their expiry; account disablement is not claimed as an immediate JWT revocation test. The agent key was independently tested as rejected after revocation.

Fictional fixture records remain for evidence and referential integrity. They are isolated from existing accounts. Their IDs are in an ignored private manifest, not in this public report. No broad database deletion or migration was performed. The report contains no passwords, bearer tokens, service credentials or existing customer data.

The [runner](../../../scripts/security-live.mts) requires an explicit live-fixture flag, uses a bounded request budget and restricts destinations. It reads local credentials privately. **Do not rerun it automatically or point generic scanners at production.** Each fresh run creates new disposable records and requires renewed operational judgement. Prefer staging when it becomes available.

## Limits and follow-up

These results cover the listed cases only. They do not establish deployed protection against load, slow streams, paid-provider abuse, every SQL function or every private field. Platform firewall/rate-limit configuration was not available for inspection, and no flood was used to discover it. Source inspection found selected database quotas; it does not prove the deployed settings or a comprehensive identity/IP budget.

The remaining [acceptance matrix](../../SECURITY_TESTING.md) includes current file-release/reversal gates, membership loss, real expiry, valid OAuth consent/exchange plus replay, prompt injection, and competing receipt submissions. This run did not execute those hosted cases. Payment and OAuth negative regression tests remain local evidence; older funded Testnet acceptance is separately dated. No new Mainnet transaction occurred.

Request-body hardening adds actual byte limits and a read deadline to OAuth registration/token and authenticated MCP POST locally. Its tests include omitted/false Content-Length, split UTF-8, stalled cancellation and an official MCP client using the bounded transport. Deploy and repeat a small authenticated smoke check before describing that hardening as live.
